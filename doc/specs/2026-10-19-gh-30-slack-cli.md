# `pi-quiver slack` CLI: post, reply, dm, canvas (#30)

**Ticket:** [jjuraszek/pi-quiver#30](https://github.com/jjuraszek/pi-quiver/issues/30)
**Goal:** Claude Code, CI, and scripts send Slack messages through the same core the pi `slack_*` tools use, via `pi-quiver slack post|reply|dm|canvas` with a one-line result and fixed exit codes; no plugin skill ships.
**Amend-grant:** every later spec amendment in this flow (corrected facts, paths, verification lines, and scope, acceptance-criteria, or public-contract edits alike) applies without asking; only a redraw (changed problem statement, component added, removed, or re-bounded) still stops for you, and the grant never stands in for a spec approval.

## Problem

`bin/pi-quiver.ts:84` rejects any command other than `fetch` and `doc-to-md` (`unknown command: slack`, exit 2), so the Slack data plane in `lib/slack-core.ts` (credential ladder, announce protocol, upload fallback, error hints) is reachable only from a pi session. Consumer repos run a hand-rolled `scripts/slack/post.py` from Claude Code and CI, duplicating token resolution and the headline-plus-thread shape, and drifting from the pi tools.

Two ticket premises were corrected against the source. "The core is pi-free" is false transitively: `lib/slack-core.ts:17` imports `resolveConfig` from `lib/extension-config.ts`, whose line 22 imports `getAgentDir` from `@earendil-works/pi-coding-agent`; `test/packed-install.test.ts` asserts the esbuild bundle contains no `@earendil-works`, so a pi-free settings seam is a prerequisite. "Installing the tarball yields a plugin manifest" is false: `package.json` `files` excludes `skills/` and `.claude-plugin/`, `test/layout.test.ts:33-44` bans them, and README "Claude Code support" documents that split. The user then decided no skill ships at all: pi gets the `slack_*` tools, Claude Code gets the CLI, and consumer command files inline the invocation; a shared skill would be a third description of the same surface.

Framing: kept - the change follows the fetch/doc-to-md shape (pi-free `lib/*-core.ts`, thin subcommand in the single `bin/pi-quiver.ts`); the corrected premises are prerequisites inside that shape.

## Downstream acceptance requirements

All six requirements ship in the first release containing the CLI; a downstream repo pins that release as its minimum. These are additions to the original ticket snapshot above, not replacements for its verbatim rows. The original row 2 headline assertion applies to `user` (including the default); row 4's normal token ladder has the explicit env-only override below; row 5's exit-4 stdout gains the required error token. All six rows are in scope.

- [ ] `post --as bot` accepts multi-line `--text`; the one-line headline assertion (`assertHeadline`) stays for `--as user`. Scheduled reports and CI audit posts are multi-line today.
- [ ] `--no-unfurl` on `post`, `reply` and `dm` sets `unfurl_links` and `unfurl_media` to false.
- [ ] `--blocks-file` is accepted on `dm` (Block Kit DMs exist today).
- [ ] `--token-from-env`: the process environment is the sole token source for that invocation - no credential command, no `.env` files. Services hold the token in-process and inject it per call.
- [ ] `--dry-run`: resolve the token and validate every argument with no network call, same exit codes (2 usage, 3 no token for the identity), so a wrapping guard can probe the full token ladder without duplicating it.
- [ ] On exit 4, stdout carries `error=<slack error code>` beside any `ts=` that landed, so a caller can tell auth-class failures (fall back to another sender) from the rest (stop).

### CLI contract

```
pi-quiver --version
pi-quiver slack --help
pi-quiver slack post   --channel <id> --text <text> [--detail <text> | --detail-file <path>] [--blocks-file <path>] [--no-unfurl] [--as user|bot] [--token-from-env] [--dry-run]
pi-quiver slack reply  --channel <id> --thread-ts <ts> (--text <t> | --text-file <p>) [--no-unfurl] [--as user|bot] [--token-from-env] [--dry-run]
pi-quiver slack dm     --user <Uxxxx> (--text <t> | --text-file <p>) [--blocks-file <path>] [--no-unfurl] [--as user|bot] [--token-from-env] [--dry-run]
pi-quiver slack canvas --id <Fxxxx> --markdown-file <path> [--as user|bot] [--token-from-env] [--dry-run]
```

- `--as` defaults to `user`, the same default as the `slack_post` tool.
- `--channel` and `--user` are raw IDs (`C...`/`D...`/`G...`, `U...`). No `#name`/`@name` lookup and no `@mention` rewriting: those live in `extensions/slack.ts` + `lib/slack-cache.ts`, not the core, and the CLI calls the core only. Text is sent as given.
- `--version` prints `package.json` `version`, located as the nearest ancestor `package.json` of `import.meta.url` (resolves from both `bin/` and `dist/bin/`), exit 0, no settings read.
- `--help` and `--version` run before any settings, token, or network access.
- Text and markdown come only from the named flag or the `--*-file` path. The CLI never touches `process.stdin`.
- `--blocks-file` on `post` or `dm` is a JSON array of Block Kit blocks (the `blocks` parameter of `chat.postMessage`); any other shape is a usage error. On `dm`, the blocks and supplied fallback text go to the opened DM's `chat.postMessage`; no blocks helper or name resolution is added.
- `--no-unfurl` is a valueless flag on `post`, `reply`, and `dm` only. It passes `unfurl_links: false` and `unfurl_media: false` to the existing core message arguments (both headline and detail when applicable). When absent the existing behavior stays; `canvas --no-unfurl` is exit 2.
- `--token-from-env` and `--dry-run` are valueless flags on all four Slack subcommands. Missing flag values for value-taking flags and unexpected values after boolean flags remain usage errors.
- `quiver.slack.enabled` is not consulted - an explicit invocation is the opt-in. Every other `quiver.slack` key (token env names, `userTokenCommand`, timeout, `uploadThresholdChars`, env overrides) resolves exactly as for the pi tools, from `<agentDir>/settings.json` and `<cwd>/.pi/settings.json`, with `agentDir` from the bin's existing `cliAgentDir(env)` (honors `PI_CODING_AGENT_DIR`).
- Token: `repoRoot = discoverRepoRoot(cwd)` (core export, what `extensions/slack.ts:224` does), then `resolveCredential(as, cfg, env, repoRoot)` unchanged. For `user` with `userTokenCommand` configured the command is the sole source (a failing command is exit 3 even when env or `.env` would have a token); otherwise the env/`.env` ladder. `bot` never runs a command. Row 4's "credential command first, then ..." is read this way.
- With `--token-from-env`, resolve Slack config as usual to obtain the identity's configured `userTokenEnv` or `botTokenEnv` name (including existing config/env overrides), then read only that key from the injected process environment. A missing or empty value is exit 3 even if a command or any `.env` could supply it. Do not invoke `resolveCredential`, a credential command, repo-root discovery for credential lookup, or any `.env` reader on this path. No new config key or core credential behavior is introduced.
- `--dry-run` uses the same parser, file reads, JSON-array checks, identity-specific text checks and token selection as a send, then returns 0 with empty stdout before any API or upload call. Usage failures remain 2 and token failures remain 3 (other local runtime failures retain exit 1). Without `--token-from-env` it exercises the complete existing token ladder, including a configured credential command; with it, only the process env is inspected. It never calls `conversations.open`, `auth.test`, permalink lookup, Slack APIs, or uploads, and does not assert that Slack will accept the credential, scopes, IDs, or blocks. No fabricated `ts=` or other success token is printed.
- Canvas: the user or bot token needs the `canvases:write` scope (Slack's `canvases.edit` reference lists it for both identities); `doc/slack.md` CLI section names it.

### Dispatch and data flow

Flags -> `parseCliArgs` (pure) -> file reads and local validation -> `resolveSlackConfig` -> selected credential path (`resolveCredential` by default, process env only with `--token-from-env`) -> dry-run returns 0 without network, otherwise dispatch -> one stdout line -> exit code.

| Subcommand | Core call | stdout |
|---|---|---|
| `post` without `--detail*` | `postMessage({ channel, text, blocks? })` | `ts=<ts> permalink=<url>` |
| `post` with `--detail*` and single-line text | `postMessage({ channel, text, blocks?, thread_body, ...unfurl })` (the announce path; blocks ride in the detail, headline stays plain) | `ts=<ts> permalink=<url> detail_ts=<ts>` |
| `post --as bot` with multi-line text and `--detail*` | CLI composes two existing core calls: `postMessage({ channel, text, ...unfurl })`, then `postMessage({ channel, text: detail, blocks?, thread_ts: parent.ts, ...unfurl })`; bypass the announce-only single-line guard without changing it | same parent `ts=` and optional `permalink=`; `detail_ts=` is the detail result's `detailTs` on upload fallback, otherwise its `ts` |
| `reply` | `postMessage({ channel, text, thread_ts })` | `ts=<ts> permalink=<url>` |
| `reply` with text over `uploadThresholdChars` | same call; the core's upload fallback posts an intro reply and uploads the text, returns `{ ts: thread_ts, detailTs }`, no permalink lookup | `ts=<thread ts> detail_ts=<intro ts>` |
| `dm` | `apiCall("conversations.open", token, { users }, { retry: true })` -> `channel.id` (missing -> `unexpected_response`, nothing sent, exit 4), then `postMessage({ channel, text, blocks?, ...unfurl })` | `ts=<ts> permalink=<url>` |
| `canvas` | `apiCall("canvases.edit", token, { canvas_id, changes: [{ operation: "replace", document_content: { type: "markdown", markdown } }] }, { retry: true })` - one call, no `canvases.create`, no permalink lookup | `canvas=<id>` |

`post --as user` (including the default) runs `assertHeadline` on `--text`; `post --as bot` accepts non-empty multi-line text and uses the existing plain core post path without a CLI one-line guard. `reply` and `dm` do not run `assertHeadline`. Before token lookup, shared local validation covers empty text, file readability and blocks-array shape. Dry-run also exercises the existing core text-size guard for plain sends, treating an invalid size as usage (exit 2); actual sends retain the existing core's exit-4 size failure. Neither mode rejects oversize threaded text that the core can upload. Reuse the existing core text-limit helper rather than duplicating the limit (an export-only change if needed); do not change core validation behavior. For the bot multi-line two-call path, a definitive detail rejection retains its Slack error code and the acknowledged parent `ts`; an uncertain detail outcome stays exit 5 with the existing empty stdout rule. The normal user announce recovery path is unchanged.

All `post`/`reply`/`dm` calls in the table carry the optional unfurl fields from `--no-unfurl`, including both bot detail calls; upload helpers retain their existing transport behavior. Result tokens are `key=value` separated by one space; a parser reads them by presence. `permalink=` is omitted when `withPermalink` returned none (the core's warning goes to stderr, exit stays 0). `detail_ts=` is `MutationResult.detailTs` - on the upload fallback that is the intro reply's ts, the first message in the thread. A `dm` whose text exceeds the core's 4000-unit limit fails locally with `text_too_long` (exit 4) after `conversations.open` and before any `chat.postMessage`; the core guard stays. Retries follow the core: `postMessage` passes `retry: true` on mutating calls and `retry: false` on the announce headline (`lib/slack-core.ts:745`, `:1106`); the CLI's own two calls pass `retry: true` (`conversations.open` as `openDm` does; `canvases.edit` because a full replace is idempotent).

### Exit codes

| Code | Condition | stdout |
|---|---|---|
| 0 | sent (permalink lookup failure still 0), or dry-run validation and credential resolution succeeded | result line for sends; empty for `--dry-run` |
| 2 | usage: unknown subcommand/flag, missing required flag, both `--text` and `--text-file`, unreadable `--*-file`, `--blocks-file` not a JSON array, `--as` not `user`/`bot`, `assertHeadline` rejects `post --as user --text`, or local validation rejects bot text | empty |
| 3 | selected credential path yields no token for the identity (`missing_token`, `credential_command_failed`), including an absent/empty process-env value with `--token-from-env` | empty |
| 4 | a definitive error: a `SlackError` from a Slack `ok:false` reply (`mapSlackApiError`, including `channel_not_found`, `not_in_channel`, `msg_too_long`, `invalid_auth`), the core's local `text_too_long`, `detail_failed`, `rate_limited` after the core's one retry, `http_<n>`, or `transport`/`unexpected_response` from the non-mutating `conversations.open` | one line `error=<code>`, or `ts=<ts> error=<code>` when the parent landed (`err.data.ts` from announce `detail_failed`, or the acknowledged parent on the bot multi-line detail path); for `reply`'s upload-fallback `detail_failed`, the data carries `thread_ts` only, so stdout is `error=detail_failed` and stderr's core message names the persisted detail path |
| 5 | outcome unknown: `outcome_unknown`; `transport` or `unexpected_response` raised by a mutating call (`chat.postMessage`, `canvases.edit`, the upload leg - the core only wraps the announce headline as `outcome_unknown`, `lib/slack-core.ts:1118`; every other fetch failure throws `transport`, `:395`); `internal_error`/`fatal_error` from `canvases.edit` (Slack documents both as possibly partially applied) | empty |
| 1 | any other throw before the first mutating request (an unreadable `.env` file, `userTokenCommand` spawn errors not already wrapped) - same meaning as `fetch`/`doc-to-md`'s runtime error | empty |

The bin wraps the injected `apiCall` to record once a mutating method (`chat.postMessage`, `canvases.edit`, `files.getUploadURLExternal`, `files.completeUploadExternal`) has been invoked; a non-`SlackError` throw after that mark (for example `SyntaxError` from `res.json()` on a 200 with a non-JSON body, `lib/slack-core.ts:432`) exits 5, before it exits 1. The core's behavior is unchanged; the classification lives in the adapter.

stderr carries `usage: <reason>` (plus USAGE) for 2, the core's error message and `ERROR_HINTS` hint for 3/4/5, and for 5 the sentence "Check the channel before retrying." Checks run in the table's order, so one input always yields one code; nothing after a code-2 or code-3 check touches the network. The resolved token never appears in output: the CLI passes every stderr/stdout string through one redaction step that replaces the credential value with `<redacted>` (a malformed token, for example one containing a newline, is quoted verbatim by `fetch`'s header validation inside the `transport` message, so filtering `err.data` alone is not enough), and prints only `SlackError.message`, `code`, and the `ts`/`channel` keys from `data`. On exit 4, `error=` is the classified `SlackError.code` (for example `invalid_auth`, `missing_scope`, `channel_not_found`, or `detail_failed`), never parsed from the human message. It passes through the same output redaction. Success, exit 1/2/3/5 stdout, and stderr behavior are otherwise unchanged. Core hints that name pi tools (`run slack_cache_refresh`, `re-invoking slack_post`) print unchanged; the `doc/slack.md` CLI section explains the CLI reading: pass raw channel IDs, and check the channel before re-running the same command.

### Packaging

`package.json` `files`, `bin`, and the esbuild command do not change. `lib/settings-core.ts` and `lib/slack-core.ts` must contain no `@earendil-works` import so the bundle purity assertion holds; `lib/slack-cache.ts` is not imported by the bin.

## Errors and edge cases

- `--detail` and `--detail-file` together, `--text` and `--text-file` together: exit 2.
- `--detail-file`/`--text-file`/`--markdown-file`/`--blocks-file` missing or unreadable: exit 2 with the path in the message; empty message text: exit 2 for either identity's `post` and for `reply`/`dm`.
- Dry-run validates supplied detail, markdown, blocks, IDs, and flags even though no send follows; invalid input is exit 2 before any credential lookup, including with `--token-from-env`. Dry-run does not introduce remote validation or new canvas/blocks content restrictions.
- `--token-from-env --as user` never uses a bot token and vice versa; a valid token for the other identity does not satisfy the invocation.
- `conversations.open` failure in `dm` (`ok:false`, `transport`, or a reply without `channel.id`): exit 4, nothing sent, no `chat.postMessage`.
- `canvases.edit` `ok:false`: exit 4 with the hint, except `internal_error`/`fatal_error` -> exit 5 (adapter mapping, scripted in tests).
- Settings lint warnings (unknown keys, legacy flat keys): stderr, not fatal, same text as the extension emits.
- `PI_CODING_AGENT_DIR` set: settings read from there, same as `doc-to-md` does today.
